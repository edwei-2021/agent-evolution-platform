# Phase M execution-ledger follow-up (執行帳本與診斷補強)

This increment connects actual nanobot work to the M queue and adds an explicitly enabled canonical ledger to the existing GUI GEPA supervisor. It also removes protected example records and raw tool bodies from GEPA reflection feedback. These are implemented integration boundaries, not a declaration that all Phase M exit criteria have passed.

## Operator paths (操作路徑)

The existing GUI/settings remain the default. With the locked M environment installed, `bash scripts/start-gui.sh --canonical` runs that same GUI under `.venv-m` and records new GEPA work in `.local/m/control.sqlite3`. The GUI labels this as ledger mode (帳本模式). It preserves the existing bounded native evaluator and existing local Skill approval; it does not claim to activate container isolation or a complete signed release bundle.

Each canonical GEPA submission freezes its configuration in content-addressed storage before dispatch, claims a fenced job lease, commits canonical RunResult/Evaluation records for every verified rollout, and persists role transitions. Terminal M results publish after provider-slot release. Startup reconciles a stale GUI view from committed canonical results or marks unfinished canonical work interrupted. Startup/recovery never sends a model request. An interrupted search is not silently resumed.

The authenticated M API additionally accepts `POST /api/m/nanobot/jobs` with exactly `task_id`, `skill_body`, `label`, `repetition`, `calls`, `seconds`, and `experiment`. Supply the existing operator bearer token and an Idempotency-Key. The server owns the evaluator image (`aep-evaluator:m`), freezes dataset/model/SDK/code/tool policy, and stores the private configuration under reserved checkpoint ordinal -1. A repeated identical request returns the same job before another dependency freeze; changed input with the same key fails. Reads and support export do not freeze or dispatch.

The explicit `python -m platform_m.worker` consumes configured native jobs as well as Mock jobs. Native dispatch requires the shared runtime lock, immutable configuration and unchanged source. A live legacy GUI keeps that lock, so queued native work waits until the GUI stops. The initial 180-second lease covers the 15-second source inventory plus one 120-second cold SDK probe and cleanup/publication allowance. During execution, the owned supervisor refreshes a 90-second lease every 20 seconds. Heartbeats never extend the frozen task deadline.

Native cancellation/deadline stops the owned process group, preserves private stdout/stderr, and refuses further model calls. Logs have a 16 MiB aggregate supervision limit; debug export retains only bounded metadata. The worker does not automatically replay an interrupted native external request. Completed comparison tasks remain reusable through the existing comparison runner.

Cancellation of running/evaluating work first enters `cancelling` (取消清理中). The owner publishes `cancelled` only after its process/container cleanup. Queued cancellation can finish immediately. Canonical GUI publication also waits for provider-slot release; a paused finalizer must leave both public views nonterminal. An expired cancelling lease becomes interrupted and is not proof of cleanup. Release replay requires a completed parent job and its committed result, so a passing but uncommitted evaluation cannot authorize a release.

## Diagnostic contract (診斷契約)

`branch.decision` entries use the existing rotating `workflows.jsonl`; failures also reach the error sidecar. They identify phase, stable branch name, outcome, Run/job correlation, elapsed time, scalar counts/limits, exception type and up to eight source-frame locations. Raw request arguments, credentials, model replies, tool bodies and protected example records are excluded. Diagnostic write failure cannot replace a successful operation or its original exception. Authoritative ledger failures still block advancement.

Covered branches include queue submission/configuration/claim, lease/state/checkpoint persistence, native model-lock admission, source rejection, process launch/cleanup, HTTP validation/permission/conflict, GEPA metric/iteration admission, fatal proposal reentry, novelty rejection, final evaluation, evidence replay, canonical publication/recovery and release registration/replay/approval/signature/activation. Native infrastructure failures preserve their original type/location and do not receive a successful evaluation.

GEPA reflection now receives public task/source plus trusted passed/total counts and fixed tool-status/rejection categories. Hidden inputs/answers and raw error strings remain in private evidence, not reflection. The policy is frozen in provenance and independently reconstructed during reviewer/approval replay. M release registration also refuses a lost validation success even when its validation total improves.

### M6 local Git/DB release reconciliation (本地發布對帳)

An approved activation commits the signed release and incremented revision to SQLite first, then stores its canonical manifest as a Git blob at `refs/agent-evolution/active` with an atomic compare-and-swap. The ref is local to the checkout; this path does not push to a remote, alter source HEAD or activate the whole runtime bundle. The database remains authoritative. Before an activation, a pending older publication is reconciled; startup also attempts reconciliation without model dispatch. It accepts a prior Git ref only when its signed release has a committed activation/rollback event. A foreign, malformed or noncanonical ref blocks publication and remains available for investigation.

Inspect with `.venv-m/bin/python scripts/m_admin.py git-status` or authenticated `GET /api/m/releases/git`. If `synchronized` is false after a Git interruption, use `.venv-m/bin/python scripts/m_admin.py reconcile --expected-revision N` or approver-only `POST /api/m/releases/reconcile` with `{"expected_revision":N}`. Obtain `N` from the preceding status response; a changed revision fails instead of publishing a stale pointer. The API startup records reconciliation failures but stays available for diagnosis. A failure after the Git ref changes but before the publication event commits is repaired on the next reconciliation, once per revision, without repeating activation.

The immutable ledger records `release.git.pending` and `release.git.published`; supplementary `.local/diagnostics/workflows.jsonl` records `release.git-observed`, `release.git-verified`, `release.git-ancestor`, `release.git-revision`, `release.db-activated`, `release.git-published` and `release.git-event-recovered` decisions, including revision and bounded source-frame error locations. A matching ref still re-verifies the signed manifest and immutable artifacts. Git timeouts during startup leave the API available and record `release.git-startup` failure for investigation. Keep the DB, the Git ref and the diagnostic bundle together when investigating an incomplete publication. The focused real-Git tests inject failures on both sides of the ref update, check startup repair and duplicate-event prevention, reject a foreign ref, and verify approver/token boundaries. This local recovery does not establish remote Git distribution or complete Phase M acceptance.
