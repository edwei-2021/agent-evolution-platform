# Incremental architecture

## Phase 1: GUI MVP (implemented)

The static GUI uses `DemoAdapter` to maintain a versioned browser-local workspace. `domain.js` owns state transitions and demo release validation; `app.js` renders views and forwards user intent. Every score and task remains explicitly synthetic. Rendering escapes imported strings before inserting HTML. JSON imports are size-limited and schema-checked.

One demo evaluation tick occurs every 1.2 seconds while the page is open. Pausing or cancelling stops ticks for that experiment. Refresh and import convert running state to paused, without pretending that a background job is running. The seeded example demonstrates the final review screen. The candidate skill fixture is not generated by a model.

## Phase 2a: Local process visibility (implemented in v0.3.0)

`serve_gui.py` now hosts same-origin runtime endpoints and supervises a fixed native-tool workflow through `runtime_service.py`. SQLite snapshots and per-run artifacts stay in `.local/`. Five real subprocess stages perform asset inspection, JavaScript tests, trusted Python tests, rule-based evidence analysis and review. The browser uses a non-overlapping polling client with a default two-second delay after each request; it shows stale data explicitly on failure. Registry configuration remains browser-local and run role bindings are immutable. No model or GEPA calls are made.

Cancellation terminates the active process group. A stage deadline bounds work; queued downstream stages are skipped after failure. One supervisor holds the checkout lock, and one workflow runs at a time. After a restart, unfinished records are marked interrupted and process liveness is unconfirmed. This is a local development service, not a durable queue or remotely authenticated agent platform. The static hosted Site does not run this Python service.

## Phase 2a extension: Measured declarative Skills (implemented in v0.4.0)

The same standard-library supervisor now dispatches either project-health tasks or a five-role skill workflow. `skill_engine.py` owns four allowlisted text rules, generated Skill bodies/hashes, objective output equality and training-only one-rule search. `skill_agents.py` freezes provenance, searches training traces, selects on validation, then evaluates held-out tasks and recomputes evidence. `skill_store.py` owns immutable SQLite versions, explicit human approval, revision-checked activation and rollback. Runtime snapshots include the separate measured skill workspace; `skill-view.js` renders candidates, curve/diff, failures, versions, trials and history with the existing polling transport.

The target is a small `normalize-support-title` fixture, with 20/10/20 distinct task/output groups. This dependency-free engine establishes the execution/evidence/version path before model integration. It does not replace the planned nanobot/GEPA free-form prompt optimizer or Python repair runner. See `docs/skill-evolution.md` for counts, gates and limitations.

## Phase 2a extension: Windows Ollama provider (implemented in v0.4.1)

`ollama_bridge.py` preserves the user-proven Windows 10 NAT approach: current IPv4 gateway, default port 11435, proxy bypass and long model-loading timeout. `configure_ollama.py` saves endpoint/model settings and shell exports without connectivity tests. The Integrations view reads settings and recorded user metadata evidence; metadata refresh and one OpenAI-compatible chat request require explicit actions. Per-request artifacts pin settings revision and actual results. Startup never probes Windows and provider actions never auto-retry. The uploaded diagnostic and ZIP tools are preserved in source control.

The provider is separate from the existing rule-based Skill workflow. Later phases add Worker/Reflector execution, bounded nanobot orchestration and GEPA candidate optimization; those implementations are described below. See [the integrated Ollama guide](ollama-wsl.md).

## Phase 2b: Bounded model Skill evaluation (implemented in v0.5.0)

`llm_engine.py` runs actual Ollama chat completions with fresh messages and strict JSON output, records raw calls and reconstructs trusted task scores. `llm_agents.py` executes Coordinator, Worker, Reflector, Evaluator and Reviewer as supervised subprocesses. One training-only reflection generates a candidate; validation selects it before held-out evaluation. `llm_store.py` persists immutable prompt Skills separately from rule versions, with evidence recomputation, revision guards and explicit approval/rollback. `llm-view.js` uses existing polling for progress, comparisons, history and version controls. Settings are pinned per run; no startup probe or automatic retry occurs.

Smoke/Full use 3/2/2 and 20/10/20 fixed splits, at most 15/101 calls, and a configurable whole-run deadline. The provider slot and workflow slot prevent local concurrent model work. This self-contained reflection engine is not a GEPA implementation; no external SDK is imported. See [the model Skill guide](llm-skill-evolution.md).

## Phase 2c: Bounded nanobot SDK task execution (implemented in v0.6.0)

The first local slice reuses the existing localhost supervisor and SQLite history. `repair_store.py` freezes one fixed Skill, fixture/code provenance, model/provider revision, SDK version and budgets. `repair_sdk.py` imports the real 0.3.5 SDK through a caller-owned `AgentLoop` and three bounded tools. `repair_agents.py` surrounds its single Worker turn with preparation, deterministic trace summary, independent evaluation and reviewer replay. The private Site ships the frontend; Python workers execute in WSL. Provider settings remain server-owned.

Implemented vertical slice: fixed `python-fix-and-verify`, one integer-clamp task, six visible/six final cases, fresh workspace/session, and only read/write solution plus fixed visible tests. Shell, network, spawn and other default SDK tools are never registered. `repair_evaluator.py` accepts a small pure-function AST subset and runs with an isolated interpreter/resource limits; this is not an arbitrary-code OS sandbox. Candidate source freezes before final tests. Reviewer replays requests/writes and recomputes measurements; a model's assertion of passing tests is not evidence. See [the runner guide](nanobot-repair.md).

Implement authentication, scoped workspace access and backend validation before enabling remote job submission. Runtime connectivity and provider/model configuration belong to a server-owned settings API; no browser API key storage. Use same-origin reverse proxy or narrowly scoped CORS and authenticated transport. Remote FastAPI submission, durable remote workers and arbitrary repository execution remain planned. The local SDK task already uses the existing Host/Origin/CSRF boundary, shared provider/workflow slots, no provider retries and supervised deadline/cancellation controls.

## Phase 3: GEPA Skill evolution (implemented in v0.7.0)

The real version-pinned GEPA 0.1.4 optimizer owns reflective mutation, minibatch acceptance, Pareto selection and final candidate choice. `gepa_sdk.Adapter` bridges it to fresh nanobot 0.3.5 SDK rollouts through the existing bounded tools and trusted AST evaluator. Only `skill_body` evolves. The server freezes the active GEPA baseline, model/provider revision, tools, session policy, SDK/code/dataset provenance and budgets before dispatch.

The grouped synthetic benchmark provides 20 training / 10 validation / 20 final tasks (Smoke 4/2/4), with parameter variants kept in one operation-family split. Training traces alone reach the reflective proposer. The adapter rejects final task IDs during search. Search uses at most 80 task evaluations with an additional hard preflight cap because GEPA stops between iterations. A separately enforced global model-call budget includes reserved independent final work and proposal requests; whole-run/per-call deadlines and process cancellation remain supervised.

After validation selection freezes, baseline and selected Skills each receive fresh validation/final executions. Reviewer replay checks actual requests, tool writes, trusted cases, candidate/selection accounting and evidence hashes. `gepa_store.py` keeps separate immutable versions and revisioned human approval/rollback. Validation must improve and final task success must not regress. Local synthetic results do not establish external benchmark quality. See [GEPA guide](gepa-evolution.md). Authenticated remote submission and arbitrary repository execution remain later work.

## Phase 4: Additional adapters and workflow evolution

Add Hermes and OpenClaw runtime adapters behind the same trace contract. Herdr can provide separate process supervision; process state is not task-success evidence. Evaluate NanoClaw for sandbox execution. Implement external workflow evolution with OpenEvolve only after the skill loop is reliable. Alternate the two loops while freezing the other layer, comparing `(S0,W0)`, `(S1,W0)`, `(S0,W1)` and `(S1,W1)` with common evaluation controls.

## Git workflow

Use an independent `nanobot-gepa-mvp` GitHub repository. Keep source, docs and tests in Git; exclude credentials and private runtime logs. Keep reviewable commits for authorized incremental work; use feature branches/PRs when a separate review is requested. A demo release in the GUI is separate from a Git software release. No CI workflow is included yet; run `npm test` before changes are submitted. Private Sites publication is independent of GitHub synchronization and must not be reported as a GitHub push.
