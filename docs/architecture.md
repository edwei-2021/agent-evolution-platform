# Incremental architecture

## Phase 1: GUI MVP (implemented)

The static GUI uses `DemoAdapter` to maintain a versioned browser-local workspace. `domain.js` owns state transitions and demo release validation; `app.js` renders views and forwards user intent. Every score and task remains explicitly synthetic. Rendering escapes imported strings before inserting HTML. JSON imports are size-limited and schema-checked.

One demo evaluation tick occurs every 1.2 seconds while the page is open. Pausing or cancelling stops ticks for that experiment. Refresh and import convert running state to paused, without pretending that a background job is running. The seeded example demonstrates the final review screen. The candidate skill fixture is not generated by a model.

## Phase 2: Real single-worker evaluation

Add a separately deployed FastAPI service, SQLite experiments/artifacts, and a durable worker. Sites hosts the browser GUI; it does not execute Python agents. Run the worker on a user-controlled server/VM with isolated task workspaces. Keep provider credentials server-side.

First vertical slice: fixed `python-fix-and-verify` skill, one nanobot worker, fixed model/tools/workflow and one executable Python repair task. Record actual commands, outputs, usage and trusted test results. Use fresh sessions, workspace and memory per evaluation. Do not accept an agent's assertion of passing tests as evidence.

Implement authentication, scoped workspace access and backend validation before enabling remote job submission. Runtime connectivity and provider/model configuration belong to a server-owned settings API; no browser API key storage. Use same-origin reverse proxy or narrowly scoped CORS and authenticated transport. This GUI has no live endpoint setting yet.

## Phase 3: GEPA skill evolution

Pin nanobot and GEPA versions after verifying their actual SDK contracts. Optimize only the skill body; freeze name and description, model, tools, memory snapshot and workflow. Group near-duplicate tasks before splitting the dataset. Initial plan: 20 training / 10 validation / 20 held-out tasks; search budget 80 evaluations. These are plans, not supplied datasets.

Return objective trusted-test success and actionable trace feedback to GEPA. Enforce timeout/token/cost limits at the runner and experiment level. The optimizer's own budget is not a substitute for agent-call limits. Keep held-out test data inaccessible to candidate generation. Evaluate the selected candidate only after search; small samples warrant limited conclusions.

A real release requires reproducible evidence, improvement criteria and explicit human review. Rejection when no candidate improves is a successful experiment outcome. Store skill hash, dataset/split hashes, evaluator revision, runtime revision, model config, memory snapshot, optimizer seed and parent version. New tasks use the activated version; running tasks retain their pinned version. Rollback moves the active pointer without deleting evidence.

## Phase 4: Additional adapters and workflow evolution

Add Hermes and OpenClaw runtime adapters behind the same trace contract. Herdr can provide separate process supervision; process state is not task-success evidence. Evaluate NanoClaw for sandbox execution. Implement external workflow evolution with OpenEvolve only after the skill loop is reliable. Alternate the two loops while freezing the other layer, comparing `(S0,W0)`, `(S1,W0)`, `(S0,W1)` and `(S1,W1)` with common evaluation controls.

## Git workflow

Use an independent `nanobot-gepa-mvp` GitHub repository. Keep source, docs and tests in Git; exclude credentials and private runtime logs. Use feature branches and PRs for subsequent changes. A demo release in the GUI is separate from a Git software release. No CI workflow is included yet; run `npm test` before changes are submitted. Private Sites publication is independent of GitHub synchronization and must not be reported as a GitHub push.
